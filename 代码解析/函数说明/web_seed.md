# web/seed.py

## 一、这个文件是干什么的

这个文件是一个**极薄的手动播种命令行入口**，全文件只有 20 行，本身不实现任何播种算法。它的职责是：让运维人员在不启动 Web 服务的前提下，直接执行 `python -m web.seed`，就往知识星云的记忆/知识库里灌入一份用于演示的种子星图。真正的播种逻辑（幂等标记、种子文件路径、写入规则、如何避免重复灌入）已经被抽走并工具化，放在 `tool/seed_knowledge.py` 里（对应工具名 `knowledge.seed`），本文件只做三件事：从那个模块导入 `SEED_FILE`、`SEED_MARK`、`seed` 三个符号；用 `__all__` 声明它们属于本模块的公开导出面；在 `if __name__ == "__main__":` 分支里拿一个运行时 manager、调用 `seed(manager)`、把结果打印出来、最后关闭 manager。它被用到的场景非常窄——只在这个文件被当作脚本直接运行时（即 `python -m web.seed`）才会执行副作用；被 `import web.seed` 时除了导入与 `__all__` 之外什么都不做。之所以保留这个入口，是为了让「不开服务也能灌演示数据」这条运维路径继续可用，同时把实现细节收敛到工具模块里，避免两份播种代码各自演化。需要注意：本文件**没有定义任何函数、方法或类**，只有模块级导入、`__all__` 赋值和一个 `__main__` 守卫块；下面的逐条详解会把这三块模块级结构当作「最接近函数的东西」逐条讲清，以保证不遗漏任何可执行单元。

## 二、函数与类逐条详解

> 说明：经完整通读（文件共 20 行，已读到末尾），本文件内**不存在 `def` 定义的函数、不存在 `async def` 定义的协程、不存在 `class` 定义的类、也不存在嵌套函数**。因此本节的逐条条目覆盖的是文件中全部三个模块级可执行结构：导入语句块、`__all__` 赋值、以及 `__main__` 守卫代码块。下面每条都按题目要求的六项（作用/参数/返回/内部流程/异常边界/同文件关系）写全，并对「非函数」这一点如实标注。

### `模块级导入语句（第 8-10 行）` （第 8 行）

- **作用**：把本文件运行所必需的全部外部符号一次性引入当前命名空间，是本文件唯一的依赖来源。它做了两件事：第一，第 8 行 `from __future__ import annotations` 启用 PEP 563 的「注解延迟求值」语义，让整个模块里所有类型注解（如果以后加）以字符串形式保存而不在运行时求值，从而可以自由书写前向引用、避免循环导入带来的运行时错误，这是项目里所有模块统一采用的头部写法；第二，第 10 行 `from tool.seed_knowledge import SEED_FILE, SEED_MARK, seed` 从工具模块 `tool/seed_knowledge` 导入三个符号——种子文件路径常量、幂等标记常量、以及真正执行播种的 `seed` 函数。之所以要这样导入，是因为本文件被刻意设计成「壳」：播种算法不能住在这里，否则运维入口和工具调用会出现两份实现，容易不一致。什么时候会被用到：只要这个模块被加载（无论是 `python -m web.seed` 直接运行，还是被别的模块 `import`），这两行就一定会执行，因此它是整个文件所有后续行为的先决条件。
- **参数**：无（导入语句不是可调用对象，没有参数列表）。若从「被导入对象」的角度看，`tool.seed_knowledge` 是模块名（包 `tool` 下的 `seed_knowledge` 模块），`SEED_FILE`、`SEED_MARK`、`seed` 是它必须对外提供的三个名字；如果该模块没有提供其中任何一个，本行在导入期就会立刻失败。
- **返回**：不返回任何值。它的效果是向本模块的全局命名空间绑定三个新名字：`SEED_FILE`、`SEED_MARK`、`seed`。绑定完成后，本文件后面的 `__all__` 和 `__main__` 块都直接引用这些名字。
- **内部流程**：第 8 行先执行 `from __future__ import annotations`，把编译器开关置为「注解不立即求值」。第 10 行再执行真正的导入：Python 先按包路径找到 `tool` 包，加载（或复用已加载的）`tool.seed_knowledge` 模块，执行该模块的顶层代码完成其初始化，然后从它的命名空间里取出 `SEED_FILE`、`SEED_MARK`、`seed` 三个属性，依次绑定到本模块的全局字典中。如果 `tool.seed_knowledge` 内部又反向导入本模块，`__future__` 注解延迟这一行能显著降低循环导入踩坑的概率。
- **异常/边界**：可能抛出的异常全部集中在第 10 行：若 `tool` 包不存在、`tool/seed_knowledge.py` 文件缺失或路径不在 `sys.path` 上，会抛 `ModuleNotFoundError`；若模块存在但其中某个名字未定义（例如被重命名或删除），会抛 `ImportError`（`cannot import name ...`）；若 `tool.seed_knowledge` 模块自身顶层代码执行时出错（例如读不到配置文件、缺少第三方依赖），该异常会原样向上冒泡，本文件不会捕获也不会兜底。对空值/非法值没有处理逻辑，因为导入期没有可校验的输入。另外 `from __future__ import annotations` 必须是文件里除 docstring 之外的第一条语句，位置错了会直接 `SyntaxError`，本文件第 8 行的位置是正确的（第 1-6 行是模块 docstring）。
- **同文件关系**：它不调用本文件里的任何东西（本文件没有可调用的东西），但它是本文件其余部分的基础——`__all__`（第 12 行）引用了它绑定的三个名字，`__main__` 块（第 15-20 行）引用了它绑定的 `seed`。也就是说，本文件内所有其他结构都依赖这一条导入。

### `__all__ = ["SEED_FILE", "SEED_MARK", "seed"]` （第 12 行）

- **作用**：显式声明本模块的公开导出面，告诉所有 `from web.seed import *` 的使用者「这个模块对外只提供 `SEED_FILE`、`SEED_MARK`、`seed` 这三个名字」。它存在的意义在于：本模块是一个纯粹的转发/再导出层，它自己没有定义任何东西，如果不写 `__all__`，`import *` 的行为会退化成「导出所有不以 `_` 开头的全局名字」，虽然当前结果碰巧相同，但一旦以后有人在这里临时 `import` 了别的辅助模块或定义了一个临时变量，`import *` 就会把它们一并泄漏出去，污染调用方命名空间。写了 `__all__` 之后，导出面被钉死，重构时不会意外改变对外契约。它也会被文档工具、静态检查工具（如 pyflakes/ruff 的未使用导入检查）当作「这些名字是被有意保留的」的信号，避免把看起来没被本文件使用的三个导入误报为无用导入。什么时候会被用到：模块被导入时立即执行；实际生效的时机是有人对该模块执行 `from web.seed import *`，或工具读取 `web.seed.__all__` 时。
- **参数**：无（这是赋值语句，不是函数）。赋的值是一个包含三个字符串字面量的列表：`"SEED_FILE"`、`"SEED_MARK"`、`"seed"`，顺序与导入顺序一致，且三个名字都必须在模块命名空间中真实存在，否则 `import *` 时会抛 `AttributeError`。
- **返回**：不返回任何值。副作用是在模块全局命名空间中创建/覆盖 `__all__` 这个变量，其类型为 `list[str]`。
- **内部流程**：构建一个三项的字符串列表，赋值给模块级名字 `__all__`。Python 解释器在后续遇到 `from web.seed import *` 时，会读取该列表并逐个 `getattr` 取名字注入导入方命名空间。列表顺序决定了 `import *` 的注入顺序。
- **异常/边界**：本行自身不会抛异常（只是列表与字符串字面量）。潜在边界在于「列表内容与真实存在的名字不一致」：如果 `tool.seed_knowledge` 改名导致第 10 行导入失败，那么第 12 行根本执行不到；如果只是把某个名字写进 `__all__` 而没导入它，则要到 `import *` 时才暴露为 `AttributeError`。本文件当前两者是一致的，没有这个问题。
- **同文件关系**：它引用的三个名字全部来自第 10 行的模块级导入；本文件内没有其他结构引用 `__all__`（它只对模块外部生效）。

### `if __name__ == "__main__":` 守卫块（第 15-20 行）

- **作用**：这是本文件唯一的「业务」代码块，也是整个模块作为命令行程序被调用时的全部实现。它实现了「手动播种」这条运维路径：直接用 `python -m web.seed` 运行时，先取得运行时的 manager 对象（连接记忆/知识存储的入口），再把 manager 交给工具层的 `seed()` 去执行幂等播种，把 `seed()` 的返回值打印到标准输出（通常是「已灌入 N 条 / 已跳过」之类的可读结果），最后调用 `manager.close()` 释放资源。用 `if __name__ == "__main__":` 包起来是刻意的：这个文件既可以被当作模块导入（此时绝对不能触发播种副作用），也可以被当作脚本运行（此时才执行播种）。第 16 行的 `from .support import get_manager` 被放在守卫块内部而不是文件顶部，也是为了「只在真的要跑脚本时才去拉 support 依赖」——因为 `web.support` 可能牵动较重的运行时初始化，导入本模块的代码不应该被迫承担这份成本，同时也降低了模块级循环导入的风险。
- **参数**：无（这是模块级代码块，不是函数，没有参数列表，也不接受命令行参数——代码里没有读 `sys.argv`，所以任何额外命令行参数都会被静默忽略）。它隐含依赖两个外部名字：从 `web.support` 导入的 `get_manager`（无参可调用对象，返回一个带 `close()` 方法的 manager），以及从 `tool.seed_knowledge` 导入的 `seed`（接受 manager、返回可打印结果的可调用对象）。
- **返回**：不返回值（模块级代码没有返回值概念）。它的可观察输出是标准输出上的一行（或多行）`print(seed(manager))` 的结果；进程退出码默认为 0，若中途抛异常则为非 0 并打印回溯。
- **内部流程**：按顺序执行四步。第一步，判断 `__name__` 是否等于 `"__main__"`——只有直接运行（`python -m web.seed`）才成立，被导入时不成立，整个块被跳过。第二步，在块内执行相对导入 `from .support import get_manager`，把 manager 工厂函数取到当前命名空间。第三步，调用 `manager = get_manager()` 得到运行时 manager 实例。第四步，调用 `print(seed(manager))`：先求值内层 `seed(manager)` 完成播种，再把其返回值交给 `print` 写到标准输出。第五步，调用 `manager.close()` 关闭 manager，释放连接/文件句柄等资源。注意第 19-20 行的顺序是「先打印、后关闭」，这意味着 `seed()` 必须在 `manager.close()` 之前把活干完（它是同步调用，天然满足）。
- **异常/边界**：本块没有任何 `try/except/finally`，因此对异常是「零兜底」的。可能出现的失败点有：`get_manager()` 抛错（运行时环境缺失、存储不可用、配置错误）；`seed(manager)` 抛错（种子文件缺失、写入失败、权限不足）；`print` 抛错（极罕见，例如标准输出已被关闭导致 `BrokenPipeError`/`OSError`）。任一环节抛异常时，后续语句都不会执行——特别地，`manager.close()` **不会**被执行，manager 只能依赖进程退出或垃圾回收来清理；这是本块在健壮性上的已知薄弱点，但也是这类一次性运维脚本的常见取舍。边界情形上：`seed` 是幂等的（幂等信息由 `SEED_MARK` 承载），所以重复运行本块不会重复灌数据，第二次运行通常会返回「已跳过」类的提示；本块不解析命令行参数，因此无法通过参数控制播种目标或强制重播；若 `seed(manager)` 返回 `None`，`print` 会输出 `None` 而不是报错。
- **同文件关系**：它调用了第 10 行导入进来的 `seed`（属于 `tool.seed_knowledge`，不是本文件定义的函数），并在此块内部按需导入 `web.support.get_manager`。本文件里没有任何函数调用它，它只由「以脚本方式运行本模块」这一外部行为触发。它不引用 `SEED_FILE` 与 `SEED_MARK`——这两个常量只是被本文件转发导出，供其他模块或工具使用。
