## 2. 逐工具明细：谁搬到了哪里

### 2.1 第 1–4 项：混合索引 / 混合召回 / 多路召回 / 图节点更新

#### `knowledge.hybrid_index` — 混合索引（双写）

**搬走的原代码**：`memory/rag/pipeline.py` 的 `RAGPipeline.ingest` 循环体内联的三步：

```python
repository.upsert_chunk(ChunkRecord(...))          # 真值源 documents/chunks + FTS5 触发器
item = self.manager.add(chunk.content, ...)         # 向量投影 memories + 向量库
repository.set_chunk_vector_status(chunk.id, "indexed")
```

**新家**（`tool/hybrid_index.py`）：

| 新名字 | 类型 | 说明 |
| --- | --- | --- |
| `index_chunk(manager, repository, *, chunk_id, document_id, chunk_index, char_start, char_end, text, metadata)` | 函数（唯一双写实现） | 顺序固定：真值源 → 向量 → 置 `vector_status`。`repository=None` 时只写向量并保持可用 |
| `repository_for(manager)` | 函数 | 复刻 `RAGPipeline.document_repo()` 的判定（非 SQLite 文档库与 `:memory:` 都返回 `None`）。后来被 5 个工具复用（对账、文档三件套） |
| `IndexMetadataEntry` / `metadata_dict` | Pydantic 模型 + 助手 | 让工具 Input 不含开放字典（严格函数 schema 禁止 `additionalProperties`） |
| `HybridIndexInput` / `HybridIndexOutput` / `HybridIndexTool` / `create_tool()` | 工具契约 | `document_id` 缺省时按 `source`→`filename`→`"manual"` 生成稳定 id，`chunk_id = f"{document_id}:{chunk_index}"` |

**调用方改动**：`RAGPipeline.ingest` 里那 3 步删掉，改成函数内延迟导入后调用 `index_chunk(...)`
（延迟导入是为了避免 `memory.rag → tool → memory.rag` 的模块级初始化环）。
原行为（含 `metadata.setdefault("source", source)`）逐字保留。

**为什么这个可分离**：它只依赖标量参数 + `manager`/`repository` 两个已存在的对象，无状态、
可幂等（`chunk_id` 既是 `chunks` 主键也是记忆 id），副作用边界清晰。

#### `knowledge.hybrid_recall` — 混合召回（向量 × FTS5，RRF 融合）

**搬走的原代码**：`memory/rag/pipeline.py` 中一次性删除的 5 个定义 + 1 个实例状态：

| 原名字 | 新名字 | 语义变化 |
| --- | --- | --- |

| `_chunk_metadata(chunk)` | `chunk_metadata(chunk)` | 公开改名 |
| `_hybrid_enabled()` | `hybrid_enabled()` | 公开改名（读 `constants.MEMORY_HYBRID`） |
| `RAGPipeline.hybrid_retrieve(query, ...) -> list[RetrievedChunk]` | `hybrid_recall(pipeline, query, ...) -> HybridRecallResult` | 返回值从裸列表变成 `HybridRecallResult(chunks, note, vector_available)` |
| `RAGPipeline.last_retrieval_note`（实例字段） | `HybridRecallResult.note` | 状态字段**删除**：同一次召回的原因与结果绑在一起，不再挂在长生命周期对象上 |

+ `pipeline.last_retrieval_note` 改为 `hybrid_recall(app.state.pipeline, ...)` + `result.note` / `result.chunks`；
`tests/test_qdrant_hybrid.py`、`tests/test_query_decompose.py`、`tests/test_web_api.py` 同步改到新 API。

#### `knowledge.multi_recall` — 多路混合召回

**搬走的原代码**（三处）：

| 原位置 / 原名字 | 新家 / 新名字 | 说明 |
| --- | --- | --- |
| `RAGPipeline.hybrid_retrieve_multi(queries, ...)` | `hybrid_recall_multi(pipeline, queries, ...)` | 每条子查询各跑「向量 + 关键词」两路，N 路名次列表一起丢给 `rrf_fuse`；单查询时**逐条委托** `hybrid_recall`，保证与单路结果完全一致 |

| — | `build_decomposer()` | 新增：有真实密钥才建 `LLMQueryDecomposer`，否则 `NullQueryDecomposer`（占位密钥 `replace-with…` 视为无密钥） |
| — | `MultiRecallInput` / `MultiRecallOutput` / `MultiRecallTool` | 工具契约：`mode` = hybrid / graph / both，`decompose` 可关；输出同时给 `sub_queries` / `hits` / `entities` / `paths` / `context` |

**顺带的提升（不是搬进工具，而是为了消除重复实现）**：`LLMKnowledgeExtractor` 的
`@staticmethod _content` / `_parse_json` 提升为 `memory/rag/knowledge.py` 的模块级公开函数
`response_content(response)` / `parse_json_object(raw)`，两个 staticmethod 删除。
理由：分解器和抽取器都要解析「OpenAI 兼容响应 → JSON 对象」，提升后**只有一份实现**。

#### `knowledge.graph_node_update` — 图节点更新/修改

四个里唯一**逻辑上最纠缠**的一个，所以拆法与前三个不同：先把"属性更新"从 `EntityResolver`
里剥出来成为唯一实现，再让原调用方委托过去。

**搬走的原代码**：`memory/rag/knowledge.py` 的 `EntityResolver.resolve` 里从 `item_id = ...`
到 `self.remember(item)` 之间的整段属性合并/写回（约 26 行），以及 `EntityResolver._store_alias`
里重复的一小段"读旧 metadata → 合并 aliases → `semantic.add`"。

**新家**（`tool/graph_node_update.py`）：

| 新名字 | 类型 | 说明 |
| --- | --- | --- |
| `update_entity_node(manager, name, *, existing, domain, entity_type, description, aliases, importance, source_id, add_written_name, item_id, create_if_missing)` | 函数（**唯一的实体节点属性写实现**） | 合并规则逐条对齐原代码：`domain`/`description` 空串=不改；`entity_type` 空串回落到旧值再回落 `ENTITY_DEFAULT_TYPE`；`aliases` 取并集且剔除 canonical；`source_ids` 取并集；`importance = max(新值, 旧值)`（只升不降）；`add_written_name` 只在"精确命中"时把用户写下的名字捐成别名 |
| `push_graph_entity(manager, name, *, domain, aliases, importance)` | 函数 | 把属性镜像到图投影，调用 `Neo4jGraphStore.update_entity(...)`；无该节点时返回 `False` |
| `find_entity_node(manager, name)` | 函数 | 按 `entity_id_for(name)` 直查，再按规范化 canonical/alias 全表扫描兜底 |
| `GraphNodeUpdateInput` / `GraphNodeUpdateOutput` / `GraphNodeUpdateTool` | 工具契约 | `side_effect="write"`；`create_if_missing=False` 时找不到节点抛 `LookupError`；输出 `created` 表示**真值源**是否新建，`graph_projected` 表示图投影里是否真的刷到了节点 |

**配套的存储层改动**：`memory/storage/graph.py` 新增
`Neo4jGraphStore.update_entity(name, *, domain, aliases, importance) -> bool`。
它**只 `MATCH` 不 `MERGE`**——"更新节点"绝不能顺手造节点，造节点仍然只由
`add_relation`/`add_observation` 负责。这一点是刻意的：`knowledge.graph_snapshot` 消费
`graph_snapshot()` 的节点集合，若更新会造节点，前端星图就会凭空多出孤立节点。
内存后端与 Cypher 后端语义一致。

**调用方改动**：`EntityResolver.resolve` 只保留"名字 → 已有实体"的匹配（精确 → 前缀 → 相似度），
属性写入改为委托 `update_entity_node(...)`；`EntityResolver._store_alias` 同样委托，仍负责把索引里
指向旧快照的 key 重指到新对象；两处都用**函数内延迟导入**。

### 2.2 第 5–6 项：三库对账与漂移自愈

`web/app.py` 的 `GET/POST /api/reconcile` 原本内联了一整套"真值源 × 向量投影 × 图投影"的对账逻辑
（`fact_items`、`projected_vector_ids`、`projected_edge_ids`、`reconcile_report`）与自愈逻辑
（`repair_drift`），共约 190 行。

| 新名字 | 类型 | 说明 |
| --- | --- | --- |
| `fact_items(manager)` / `is_fact_item(item)` | 函数 | 判定"这条语义记忆是不是一条事实"，是三个投影的共同口径 |
| `projected_vector_ids(manager)` / `projected_edge_ids(manager)` | 函数 | 枚举两个投影的 id 集合（向量侧要求实现 `list_ids`） |
| `reconcile_report(manager, repository, *, include_ids=True)` | 函数 | 返回 `DRIFT_KINDS` 五类漂移的计数与样本 id；`REPAIRABLE_KINDS` 标明哪几类可自动修 |
| `reconcile.py` 工具契约 | read | 只报告不修，因此 `side_effect="read"`、免确认、可并行 |
| `repair_drift(manager, repository, kinds)` | 函数（`tool/repair_drift.py`） | 按类自愈：未知类别抛 `ValueError`；`orphan_vector`（向量里有、真值源没有）**拒绝自动删**，因为无法区分"投影多余"与"真值源丢行"，误删即不可恢复 |
| `repair_drift.py` 工具契约 | write | `side_effect="write"`，必须确认 |

**关键取舍**：自愈工具的"可修类别"是**显式白名单**（`REPAIRABLE_KINDS`），而不是"凡漂移就修"。
`repair_drift` 通过 `reconcile` 复用同一份漂移定义（工具→工具导入），因此"报什么"与"修什么"
永远不会漂移。

### 2.3 第 7–8 项：导入 / 导出

| 工具 | 搬走的实现 | 新名字 |
| --- | --- | --- |
| `knowledge.export`（read） | `web/app.py` 的导出载荷构造 + 文件名生成 | `export_payload(manager, *, include_expired=False, limit=0, exported_at=None)`、`export_filename(stamp=None)`、`EXPORT_FORMAT = "knowledge-nebula-export/v1"` |
| `knowledge.import`（write） | `web/app.py` 的上传解析 + 逐条写入循环 + `_reject_json_constant` | `parse_import_payload(raw: bytes) -> list[Any]`（拒绝 `NaN`/`Infinity`，非法载荷抛 `ValueError`）、`import_items(manager, entries, *, max_errors=WEB_IMPORT_ERRORS_MAX)` |

### 2.4 第 9–12 项：星图 / 领域 / 孤儿 / 清理提案

这一组原本是 `web/` 下的三个模块，**文件整体删除**：

| 原文件 | 行数 | 去向 |
| --- | --- | --- |
| `web/graph_builder.py` | 567 | → `tool/graph_snapshot.py`（696 行，含 `build_graph` / `domain_color` / `_node` / `_entity_aliases` / `_date` 原样搬迁），工具名 `knowledge.graph_snapshot` |
| `web/domain_classifier.py` | 111 | → `tool/domain_classify.py`（`DOMAIN_KEYWORDS` / `KNOWN_DOMAINS` / `classify_domain` / `majority_domain`），工具名 `knowledge.classify_domain` |
| `web/cleanup.py` | 95 | → `tool/orphan_entities.py`（`find_orphan_entities` / `orphan_summary`，`knowledge.orphan_entities`）+ `tool/propose_cleanup.py`（`propose_orphan_cleanup`，`knowledge.propose_cleanup`） |

**这一组里有三处值得单独说明的设计**：

1. **`knowledge.graph_snapshot` 的节点集合是"真值源"而不是"图投影"**：星图要能显示
   "只存在于图投影里的边"（`graph_only` 边），所以 `build_graph` 把 `graph_store` 的边与
   语义记忆里的实体合并，并给出 `graph_source`（`neo4j` / `inmemory`）与 `as_of` 时间点，
   让前端能解释"这张图是哪来的、什么时刻的"。
2. **`knowledge.classify_domain` 是纯函数**：关键词表 + 打分，无 IO、无状态，
   因此 `side_effect="read"`、可并行；`build_graph_context` 通过函数内导入复用同一份 `KNOWN_DOMAINS`，
   保证"入库时判的领域"与"事后查的领域"是同一套规则。
3. **`knowledge.propose_cleanup` 故意不返回 `confirm_token`**：它把"提议删除孤儿实体"
   变成 Agent 可调用的能力，但**确认令牌只走人工通道**（`propose_orphan_cleanup` 函数本体签名与
   返回值一字未改，Web/脚本仍拿到令牌）。工具输出改为 `requires_human_confirmation=True`。
   理由：如果工具把令牌一起返回，模型就能自我确认一次破坏性删除——这是**安全边界**，
   不是实现细节。

### 2.5 第 13–15 项：文档中心（列表 / 详情 / 单文档重嵌入）

`documents`/`chunks` 是向量与图的**真值源**，所以"库里有哪些文档、各自什么状态、某篇原文是什么"
是检索前最该先问的问题。这三个工具共用 `tool/_documents.py` 的序列化助手，仓储一律复用
`tool/hybrid_index.repository_for`（`:memory:` → `None`）。

| 工具 | 新名字 | 关键语义 |
| --- | --- | --- |
| `knowledge.document_list`（read） | `list_documents(repository, *, tag, status, page, page_size)` | 分页 + 过滤 + 每篇 `chunk_count`；`page_size` 上限校验随逻辑迁入，错误文案与旧端点**逐字一致**（调用方只需把 `ValueError` 映射成 422） |
| `knowledge.document_get`（read） | `get_document(repository, document_id)` | 元数据 + 原文 + 全部分块（含 `vector_status`）；缺失文档抛 `LookupError`；`max_chunks` **只裁剪返回列表**，`chunk_count` 始终是全量 |
| `knowledge.document_revectorize`（write） | `revectorize_document(manager, repository, document_id, *, confirm_rebuild=False)` | **保留旧的闸门顺序**：先 `apply_embedding_lock` 再看文档是否存在、是否有分块。顺序不能换——锁不一致必须先报 409，否则会往错误的向量空间里写；状态推进保留 `extracted`，否则置 `vectorized` |

**Web 端点瘦身**：三个端点变成"取仓储 → 调纯函数 → 映射错误码"，只保留
`ValueError→422`、`LookupError→404`、`EmbeddingLockMismatch→409`、其余→`raise_embedding_http`+502。

### 2.6 第 16–18 项：事实写入 / 播种 / 图片入库

| 工具 | 新名字 | 关键语义 |
| --- | --- | --- |
| `knowledge.add_fact`（write） | `add_fact(manager, *, subject, predicate, object, domain="", note="", confidence=1.0)` | 事实是知识图谱的**边**：一次写入同时落真值源与图投影，是最小可审计的写入单元。与 `memory.add`（写内容）刻意分开；领域留空落 `DEFAULT_DOMAIN`、上限复用 `WEB_FACT_*` 常量 |
| `knowledge.seed`（write） | `seed(manager, path=None)`、`SEED_MARK`、`SEED_FILE` | 幂等依据是**库内** `metadata.seed == SEED_MARK`（不是外部状态文件），库被复制/清空/换机都自动跟随；`SEED_FILE` 以工具文件位置锚定仓库内 `web/seed_data.json` |
| `knowledge.ingest_image`（write） | `ingest_image(pipeline, *, image, text="", mime_type="image/jpeg", metadata=None)` | 图片字节是感知记忆的**原始载荷**；图上的边只能来自结构化视觉抽取器，绝不来自向量相似度；抽取失败**不回滚**已入库的图片，错误进 `extraction.errors`；非 VL 嵌入时输出诚实提示 `warning` |

**`knowledge.ingest_image` 的拆法**：实现整体搬进工具，`RAGPipeline.ingest_media` 保留为
**薄委托**（一行函数内导入 + 读回刚写入的项），因此该方法的签名、返回类型（`MemoryItem`）与
副作用（`last_ingest_report`）不变，多模态测试零改动通过。工具侧入口按**路径**读图片
（Agent 手上是路径），用 `tool/_shared` 做工作区包含性校验 + `MAX_UPLOAD_BYTES` 大小上限，
MIME 留空按扩展名推断。`pipeline` 的私有 `_accepts_parameter` 因此更名为公开的
`accepts_parameter`（抽取器协议自省），文本入库与图片入库共用一处 `inspect.signature` 逻辑。

**`knowledge.seed` 与 `knowledge.orphan_entities` 的跨工具契约**：种子实体即使完全孤立
（没有任何关系/提及/备注）也**不能**被判为清理候选——判定依据就是 `metadata.seed` 标记。
这条契约在两个工具的测试里都被锁住。

### 2.7 第 19 项：知识库规模统计（收口时补的一刀）

#### `knowledge.stats` — 库规模统计

**搬走的原代码**：`web/app.py` 的 `GET /api/stats` 端点方法体（9 行内联聚合）：

```python
manager = the_manager()
repository = app.state.pipeline.document_repo()
counts = repository.stats() if repository is not None else {"documents": 0, "chunks": 0, "chunks_indexed": 0}
return {**counts, "facts": len(fact_items(manager)),
        "memories_total": len(manager.document_store.list(include_expired=True))}
```

**新家**（`tool/knowledge_stats.py`）：

| 新名字 | 类型 | 说明 |
| --- | --- | --- |
| `knowledge_stats(manager, repository=None)` | 函数（唯一统计口径） | 真值源计数（`repository.stats()`）＋ `facts`（复用 `tool/reconcile.py` 的 `fact_items`）＋ `memories_total`（含过期项）。`repository=None` 时文档/分块按 0 返回，与旧端点逐字一致 |
| `KnowledgeStatsInput` / `KnowledgeStatsOutput` | Pydantic 模型 | 输入无参数；输出只有 5 个非负整数计数，**没有任何正文字段**（有测试断言内容不会出现在输出里） |
| `KnowledgeStatsTool` / `create_tool()` | 工具契约 | `side_effect="read"`、幂等、可并行、30s 超时；manager 缺省时走 `tool/_memory.build_default_manager()`，仓储走 `tool/hybrid_index.repository_for()` |

**调用方改动**：`web/app.py` 的 `/api/stats` 从 9 行内联实现缩成 1 行委托
（`knowledge_stats(the_manager(), app.state.pipeline.document_repo()).model_dump()`），
`fact_items` 的导入随之从 `web/app.py` 移除；`app.py` 由 820 行降到 816 行。
`tests/test_web_api.py` 里原有的 `/api/stats` 字段断言未改动且仍然通过——这正是"能力搬走、
端点行为不变"的证据。

**为什么这个可分离**：它是纯只读聚合（只依赖 `manager` 与 `repository` 两个已存在对象），
无 Web 运行时状态、无请求上下文、无副作用；搬走后同一份口径既服务仪表盘端点，
也能让 LLM 直接回答「库里现在有多少内容」，并可用 `chunks_indexed < chunks` 判断投影是否落后。

## 3. 明确拒绝：这些我没有分离，以及为什么

按你的要求，不可分离的直接拒绝，去分离其他的。以下是逐项拒绝理由（都是读代码后得出的结论）。

| 你点名/看起来可分离的对象 | 结论 | 拒绝理由 |
| --- | --- | --- |
| **四层记忆本体**：`WorkingMemory`/`EpisodicMemory`/`SemanticMemory`/`PerceptualMemory` + `MemoryManager.add/search/list/clear` | **拒绝** | 它们不是"能力"而是**数据存储契约**。`manager.add` 必须在同一进程内同时写 `memories` 行与向量库，跨工具边界调用会把它变成两次独立 RPC：真值源成功、向量失败时无法回滚，直接破坏 `memory/embedding_lock.py` 维护的一致性。而且入参/出参是 `MemoryItem`（含 `datetime`、`Mapping` 元数据），不满足工具的严格 JSON 契约 |
| **`RAGPipeline.ingest` 本体** | **拒绝**（但其可分离部分已分离） | 它是**有状态编排**：解析 → 分块 → 双写 → LLM 抽取 → 图事实物化 → 报告，全程持有 `EntityResolver` 缓存与 embedding lock。可分离的"双写"已搬成 `knowledge.hybrid_index`，剩下的编排留在管道里 |
| **`EntityResolver` 的匹配逻辑**（`_exact`/`_prefix_candidate`/`_entity_similarity`） | **拒绝** | 与实例内的 `self._index`/`self._entities` 缓存强耦合，且相似度判定需要**整个实体集合**作为上下文；做成工具就得每次全量重载实体表，既是性能倒退，也会因缓存不共享而产生与管道内不一致的结果。只分离了属性更新 |
| **`materialize_extraction`**（图事实物化） | **拒绝** | 入参是 `ExtractionResult` + `source_item`（非标量、含 `datetime`），内部是"断言/取代/撤回"三类补丁的**多步事务**，中途失败必须整体不留痕。工具契约是"一次调用一个结果"，装不下事务语义 |
| **`GraphRAGPipeline.retrieve` / `build_context`** | **拒绝** | 能力已被现有工具覆盖：`memory.rag_search` 的 `action=graph_retrieve` / `graph_context` 就是它。再注册一个只是同一实现的第二个入口，违反"一份实现"的目标 |
| **FastAPI 路由处理器**（`web/app.py` 的 20 个端点） | **拒绝** | 它们**本身就是**外部入口边界，不是内部可复用能力；把路由再包成工具只会多一层无意义的转发。本轮做的是**把路由体内的能力抽走**，路由只留校验与错误码映射 |
| **`/api/health` 状态聚合** | **拒绝**（本轮新增判断） | 它报告的是**应用自己怎么装配的**：`chat_ready()` 要读 `config/provider.toml` 并区分占位 key，`search_available()` 要读 `config/services.toml` 的 `[search]` 段，还要报告当前 embedding 实现与三个存储后端。把它工具化等于把"应用装配细节"搬进工具层，收益低而漂移风险高（工具造的是自己的管道，与 Web 实例不是同一个） |
| **`web/ingest_queue.py` + `POST /api/knowledge` 的异步作业** | **拒绝**（本轮新增判断） | 线程池、作业表、重试与关机回收是**Web 基础设施**（进程生命周期的一部分），不是知识能力。它调用的入库能力本身已经是 `memory.rag` 工具 |
| **`RAGPipeline.ingest_source` / `POST /api/ingest` 的上传编排** | **拒绝**（本轮新增判断） | 上传落盘、`base_dir` 包含性、权限字段与错误码都是 HTTP 关注点；文件入库的能力已被 `memory.rag` 工具（原文入库）与 `knowledge.hybrid_index`（分块投影）覆盖，再包一层只是转发 |
| **`web/app.py` 的 `guard_embedding` / `raise_embedding_http`** | **拒绝**（收口轮复核） | 它们只做一件事：把 `memory/embedding_lock.py` 的 `EmbeddingLockMismatch` 映射成 HTTP 409。能力本体（锁语义、维度不一致判定、`confirm_rebuild` 闸门）本来就在 memory 层，端点只是错误码适配；工具没有 HTTP 状态码可抛，包成工具没有意义 |
| **`web/app.py` 的 `graph_cache` / `invalidate_graph` / `bump_graph_revision`** | **拒绝**（收口轮复核） | 进程内缓存与 revision 计数属于 **Web 运行时状态**（与 `/api/graph?since=` 的"无变化"语义绑定），不是知识能力；星图重建能力本身已经是 `knowledge.graph_snapshot` |
| **`POST /api/graph-rag`** | **拒绝**（收口轮复核） | 它就是 `pipeline.graph_retrieve(...) + build_context()` 的三行转发，与 `memory.rag_search` 的 `action=graph_retrieve` / `graph_context` 是同一份实现；再注册只是同一能力的第二个入口 |
| **`web/support.py` 的 Agent/工具白名单装配** | **拒绝**（本轮新增判断） | `CHAT_TOOL_ALLOWLIST` / `chat_tool_names` / `get_agent` 决定"聊天回合给模型看哪些工具"，是**应用装配决策**；工具层无权决定自己是否被暴露 |
| **`tool/_memory.py` / `tool/_shared.py` / `tool/_documents.py`** | **拒绝**（本轮新增判断） | 见 §1 末表：依赖装配、安全策略、共享序列化助手。它们不是能力，注册成工具会破坏"一份实现"与安全边界 |
| **`web/cleanup.py` 的 `propose_orphan_cleanup`** | **已改判：现在分离了** | 早期审查曾以"人工审核流程的一部分、不适合作为 LLM 工具"为由拒绝。本轮重新评估后认为"提议清理孤儿实体"本身是知识治理能力，应当可调用；**但把 `confirm_token` 从工具输出里摘掉**，破坏性确认仍只能走人工通道（见 §2.4 第 3 点）。原函数签名与返回值保持不变 |

## 5. 行为影响与兼容性

- **对外行为不变**：515 个测试全绿，其中包含聊天溯源面板字段、入库双写与 `vector_status`、

  星图节点集合与重构前一致。

  与 `CHAT_CONFIRMED_TOOLS`（仅 `memory.add`）**未改动**。这是刻意的：新工具里有一半是写工具，

  只放开只读工具则是任意的部分改动。所有新工具通过自动发现已注册、可被 `Agent` 调用、
  可被 `tool.catalog` 列出。若要让聊天 LLM 直接用上只读工具，把工具名加进

## 8. 提示词增强：让模型「照着契约用工具、按任务守纪律」

这一阶段与工具分离是同一目标的两面：工具拆出去之后，模型必须知道**每个工具怎么用**、
**什么情况下不要用**。改动分三轮（151–153），全部落在提示词层，**不改任何工具执行逻辑**。

### 8.1 工具契约完整注入（151）

新增 `core/tool_docs.py`：把 `ToolSpec` 渲染成逐变量的中文契约，ReAct 与原生 function-calling
两条链路共用同一份渲染。

| 渲染行 | 内容 | 来源 |
| --- | --- | --- |
| 头部 | `- knowledge.hybrid_recall@1.0.0 [只读 · 免确认 · 超时 30s · 幂等 · 可并行]` | `ToolSpec` 元数据 |
| 用途 | `spec.description` | 工具文件 |
| 使用规范 | `spec.guidance` | 工具文件（151 新增字段，152 逐条补写） |
| 输入变量 | 逐字段：类型（含 `数组[…]` / `对象{…}` / `枚举[…]` / `A \| 空`）、必填或默认值、约束（长度/范围/枚举/pattern）、字段说明 | pydantic `model_json_schema()` |
| 输出字段 | 同上 | 同上 |
| 副作用与确认 | 写工具写明「必须持有该工具的人工确认钥匙，模型不得自行假定已授权」 | `side_effect` |
| 推荐前置 | `recommended_before_tools` | `ToolSpec` |

- 渲染顺序 = 工具名排序 + 字段定义顺序，且无时间戳 ⇒ **逐字节稳定**，OpenAI 前缀缓存（KV cache）可复用。
- 嵌套 `$ref` 展开深度与单工具字段行数有上限（`MAX_REF_DEPTH` / `MAX_FIELD_LINES`），防止提示词被单个工具撑爆。
- **`guidance` 不进 `schema_hash`**：润色提示词不会让已存的写确认钥匙失效（刻意设计，有测试守护）。
- 接线位置：ReAct 的 `Available tools` 段与热加载完整段（`agents/react.py`）；原生 function-calling 在
  `All registered tool names` 之后追加同一份契约（`agents/agent.py`），`tools` 字段继续提供机器可读 Schema。
- 当前规模：30 个自动发现工具 ⇒ 465 行 / 29174 字符（再加上 `system.tool_catalog` 的契约）。

### 8.2 逐工具使用规范（152）

31 个工具（30 个自动发现 + `system.tool_catalog`）每个都写了 `guidance`，每条都回答三件事：
**何时用 / 何时不要用（并指出该改用哪个）/ 必须遵守的硬约束**。最容易混用的边界都写进了规范：

| 容易混用的工具对 | 规范里写的边界 |
| --- | --- |
| `knowledge.hybrid_index` vs `memory.rag` vs `knowledge.add_fact` | 写原文分块 / 入库并抽取 / 写结构化事实，三者不可互相替代 |
| `knowledge.graph_node_update` vs 入库 | 只能改已存在节点；别名只增不减、重要度只升不降；`create_if_missing=false` 找不到就报错 |
| `knowledge.reconcile` vs `knowledge.repair_drift` | 先只读对账拿类别，再按类别修；只补投影，`orphan_vector` 必须由人决定 |
| `knowledge.orphan_entities` vs `knowledge.propose_cleanup` | 前者只读找候选，后者只建提案；提案返回里**没有确认令牌**，模型无法自我确认 |
| `memory.propose_delete` vs `memory.manage` | 前者提案、后者执行且必须有用户确认 |
| `knowledge.hybrid_recall` vs `knowledge.multi_recall` | 单问句用前者；多实体/关系链路用后者 |
| `memory.query` vs `knowledge.hybrid_recall` vs `memory.rag_search` | 四层记忆 / 文档分块 / 图事实与上下文块 |
| `knowledge.ingest_image` | 路径必须位于工作区内；`warning` 非空必须告知用户；抽取失败不回滚已入库图片 |

`tool/tool_template.py` 的 `guidance` 写成「这一段该写什么」的模板说明；
`tool/README.md` 同步补上字段说明与「工具契约如何进入提示词」一节。

### 8.3 按任务类型分节的系统提示词（153）

`agents/prompts.py` 把行为规范拆成 9 个具名块，由 `build_system_prompt()` 组合；
`web/support.py` 的 `SYSTEM_PROMPT` 改为组合结果（1928 字符 / 40 行）。

| 分节 | 管什么 |
| --- | --- |
| 身份总则 | 先在知识库找证据，再基于证据用中文简洁回答 |
| 检索纪律 | 先检索后回答；四类检索入口各司其职；引用原文前必须 `document_get` 核对；降级/空结果如实说明；supersede 后只采信当前值 |
| 时间纪律 | 相对时间先取 `system.current_time` |
| 写入纪律 | 五类写入各用哪个工具；先查重再写；确认类错误不重试而应告知用户；破坏性操作走提案与人工确认 |
| 一致性治理纪律 | 先对账再修；清理走提案；重嵌入不得用 `confirm_rebuild` 掩盖配置错误 |
| 多模态纪律 | 路径包含性限制如实转述；`warning` 非空必须告知 |
| 诚实与引用 | 不编造、不谎称执行、来源与链接必须标注 |
| 联网 / 离线模式 | 以「本次工具清单里有没有 `web.search`」为判据，两种规则同写在一份提示词里 ⇒ 共享 agent 单例不必按请求改写系统提示词（线程安全） |

`agents/react.py` 的 `REACT_INSTRUCTIONS` 追加「工具使用纪律」四条：只调用 `Available tools` 列出的工具、
调用前读完整契约（必填不能省、取值须满足约束、不得自创变量名或添加未声明字段）、
写工具确认错误不要重复重试、工具报错必须如实转述且不得编造 Observation。
