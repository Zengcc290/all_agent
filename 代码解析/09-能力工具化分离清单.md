## 2. 逐工具明细：谁搬到了哪里

### 2.1 `knowledge.hybrid_index` — 混合索引（双写）

**搬走的原代码**：`memory/rag/pipeline.py` 的 `RAGPipeline.ingest` 循环体内联的三步：

```python
repository.upsert_chunk(ChunkRecord(...))          # 真值源 documents/chunks + FTS5 触发器
item = self.manager.add(chunk.content, ...)         # 向量投影 memories + 向量库
repository.set_chunk_vector_status(chunk.id, "indexed")
```

**新家**：

| 新名字 | 类型 | 说明 |
| --- | --- | --- |
| `index_chunk(manager, repository, *, chunk_id, document_id, chunk_index, char_start, char_end, text, metadata)` | 函数（唯一双写实现） | 顺序固定：真值源 → 向量 → 置 `vector_status`。`repository=None` 时只写向量并保持可用 |
| `repository_for(manager)` | 函数 | 复刻 `RAGPipeline.document_repo()` 的判定（非 SQLite 文档库与 `:memory:` 都返回 `None`） |
| `IndexMetadataEntry` / `_metadata_dict` | Pydantic 模型 + 助手 | 让工具 Input 不含开放字典（严格函数 schema 禁止 `additionalProperties`） |
| `HybridIndexInput` / `HybridIndexOutput` / `HybridIndexTool` / `create_tool()` | 工具契约 | `document_id` 缺省时按 `source`→`filename`→`"manual"` 生成稳定 id，`chunk_id = f"{document_id}:{chunk_index}"` |

**调用方改动**：`RAGPipeline.ingest` 里那 3 步删掉，改成函数内延迟导入后调用
`index_chunk(...)`（延迟导入是为了避免 `memory.rag → tool → memory.rag` 的模块级初始化环）。
原行为（含 `metadata.setdefault("source", source)`）逐字保留。

**为什么这个可分离**：它只依赖标量参数 + `manager`/`repository` 两个已存在的对象，无状态、
可幂等（`chunk_id` 既是 `chunks` 主键也是记忆 id），副作用边界清晰。

### 2.2 `knowledge.hybrid_recall` — 混合召回（向量 × FTS5，RRF 融合）

**搬走的原代码**：`memory/rag/pipeline.py` 中一次性删除的 5 个定义 + 1 个实例状态：

| 原名字 | 新名字 | 语义变化 |
| --- | --- | --- |
| `_rrf_fuse(rank_lists, *, k=60)` | `rrf_fuse(...)` | 仅公开改名，`RRF_K = 60` 提为模块常量 |
| `_vector_hits(query, ...)` | `vector_hits(pipeline, query, ...)` | **不再写 `self.last_retrieval_note`**，改为返回 `(hits, note)`，降级原因随数据流动 |
| `_chunk_metadata(chunk)` | `chunk_metadata(chunk)` | 公开改名 |
| `_hybrid_enabled()` | `hybrid_enabled()` | 公开改名（读 `constants.MEMORY_HYBRID`） |
| `RAGPipeline.hybrid_retrieve(query, ...) -> list[RetrievedChunk]` | `hybrid_recall(pipeline, query, ...) -> HybridRecallResult` | 返回值从裸列表变成 `HybridRecallResult(chunks, note, vector_available)` |
| `RAGPipeline.last_retrieval_note`（实例字段） | `HybridRecallResult.note` | 状态字段**删除**：同一次召回的原因与结果绑在一起，不再挂在长生命周期对象上 |
| — | `fuse_hits(repository, rank_lists, scores, *, limit)` | 新拆出的融合+回查段（RRF 排序 → `repository.get_chunk` → 真值源没有的分块不返回） |
| — | `HybridRecallInput` / `HybridHit` / `HybridRecallOutput` / `HybridRecallTool` | 工具契约（`side_effect="read"`，只读免确认） |

**调用方改动**：
- `web/app.py`（聊天 U4 溯源面板）从 `app.state.pipeline.hybrid_retrieve(...)` + `pipeline.last_retrieval_note`
  改为 `hybrid_recall(app.state.pipeline, ...)` + `result.note` / `result.chunks`；
- `tests/test_qdrant_hybrid.py`、`tests/test_query_decompose.py`、`tests/test_web_api.py` 同步改到新 API。

**为什么这个可分离**：单次调用、无写副作用、输入输出都是可序列化标量，正是工具契约的理想形状。

### 2.3 `knowledge.multi_recall` — 多路混合召回

**搬走的原代码**（三处）：

| 原位置 / 原名字 | 新家 / 新名字 | 说明 |
| --- | --- | --- |
| `RAGPipeline.hybrid_retrieve_multi(queries, ...) -> list[RetrievedChunk]` | `hybrid_recall_multi(pipeline, queries, ...) -> HybridRecallResult` | 每条子查询各跑「向量 + 关键词」两路，N 路名次列表一起丢给 `rrf_fuse`；单查询时**逐条委托** `hybrid_recall`，保证与单路结果完全一致 |
| `GraphRAGPipeline.retrieve_multi(queries, ...) -> GraphRAGResult` | `graph_recall_multi(pipeline, queries, ...) -> GraphRAGResult` | 每条子查询各做 seed+expand，路径按 `effective` 合并去重（同 `(entities, relations)` 取权重高者），evidence 按 id 去重 |
| `memory/rag/knowledge.py` 的 `QueryDecomposer`（Protocol）/ `NullQueryDecomposer` / `LLMQueryDecomposer` | 同名整体迁移到 `tool/multi_recall.py` | 分解器是「多路」的前置步骤，与多路召回同属一个能力，故一起搬 |
| — | `build_decomposer()` | 新增：有真实密钥才建 `LLMQueryDecomposer`，否则 `NullQueryDecomposer`（占位密钥 `replace-with…` 视为无密钥） |
| — | `MultiRecallInput` / `MultiRecallOutput` / `MultiRecallTool` | 工具契约：`mode` = hybrid / graph / both，`decompose` 可关；输出同时给 `sub_queries` / `hits` / `entities` / `paths` / `context`，便于调用方核对"到底跑了哪几条" |

**顺带的提升（不是搬进工具，而是为了消除重复实现）**：
`LLMKnowledgeExtractor` 的 `@staticmethod _content` / `_parse_json` 提升为 `memory/rag/knowledge.py`
的模块级公开函数 `response_content(response)` / `parse_json_object(raw)`，两个 staticmethod 删除。
理由：分解器和抽取器都要解析「OpenAI 兼容响应 → JSON 对象」，提升后**只有一份实现**，
且不需要为解析去实例化抽取器。`__all__` 已补入这两个名字。

**为什么这个可分离**：它是"对同一批已入库数据的多路只读查询 + 结果融合"，无写副作用，
输入是字符串列表，输出可完整序列化。

### 2.4 `knowledge.graph_node_update` — 图节点更新/修改

这是四个里唯一**逻辑上最纠缠**的一个，所以拆法与前三个不同：先把"属性更新"从
`EntityResolver` 里剥出来成为唯一实现，再让原调用方委托过去。

**搬走的原代码**：`memory/rag/knowledge.py` 的 `EntityResolver.resolve` 里从
`item_id = ...` 到 `self.remember(item)` 之间的整段属性合并/写回（约 26 行），以及
`EntityResolver._store_alias` 里重复的一小段"读旧 metadata → 合并 aliases → `semantic.add`"。

**新家**：

| 新名字 | 类型 | 说明 |
| --- | --- | --- |
| `update_entity_node(manager, name, *, existing, domain, entity_type, description, aliases, importance, source_id, add_written_name, item_id, create_if_missing)` | 函数（**唯一的实体节点属性写实现**） | 合并规则逐条对齐原代码：`domain`/`description` 空串=不改；`entity_type` 空串回落到旧值再回落 `ENTITY_DEFAULT_TYPE`；`aliases` 取并集且剔除 canonical；`source_ids` 取并集；`importance = max(新值, 旧值)`（只升不降）；`add_written_name` 只在"精确命中"时把用户写下的名字捐成别名（前缀/模糊命中不捐，避免污染相似实体） |
| `push_graph_entity(manager, name, *, domain, aliases, importance)` | 函数 | 把属性镜像到图投影，调用 `Neo4jGraphStore.update_entity(...)`；无该节点时返回 `False` |
| `find_entity_node(manager, name)` | 函数 | 按 `entity_id_for(name)` 直查，再按规范化 canonical/alias 全表扫描兜底 |
| `GraphNodeUpdateInput` / `GraphNodeUpdateOutput` / `GraphNodeUpdateTool` | 工具契约 | `side_effect="write"`；`create_if_missing=False` 时找不到节点抛 `LookupError`；输出 `created` 表示**真值源**是否新建，`graph_projected` 表示图投影里是否真的刷到了节点 |

**配套的存储层改动**：`memory/storage/graph.py` 新增 `Neo4jGraphStore.update_entity(name, *, domain, aliases, importance) -> bool`。
它**只 `MATCH` 不 `MERGE`**——"更新节点"绝不能顺手造节点，造节点仍然只由
`add_relation`/`add_observation` 负责。这一点是刻意的：`web/graph_builder.build_graph()`
消费 `graph_snapshot()` 的节点集合，若更新会造节点，前端星图就会凭空多出孤立节点。
内存后端与 Cypher 后端（`CASE WHEN $domain = '' … / size($aliases) = 0 … / $importance IS NULL …`）
语义一致。

**调用方改动**：
- `EntityResolver.resolve` 只保留"名字 → 已有实体"的匹配（精确 → 前缀 → 相似度），
  属性写入改为委托 `update_entity_node(...)`；
- `EntityResolver._store_alias` 同样委托（`aliases=[name]`、`importance=item.importance`、`item_id=item.id`），
  仍负责把索引里指向旧快照的 key 重指到新对象；
- 两处都用**函数内延迟导入**（`from tool.graph_node_update import update_entity_node`），
  避免 `memory.rag.knowledge → tool → tool._memory → memory.rag` 的初始化环；
- `tool/*.py` 一侧同样把 `_memory` 的导入收进函数（`_default_manager()` / `_default_pipeline()`），
  这样工具模块被 `memory.rag` 反向导入时也不会触发半初始化。

**为什么这个可分离**：属性更新本身是纯数据操作（读旧 metadata → 合并 → 写回 + 图投影），
与"匹配"正交。拆开后 `EntityResolver` 的匹配职责与工具的写入职责各自单一。

## 3. 明确拒绝：这些我没有分离，以及为什么

按你的要求，不可分离的直接拒绝，去分离其他的。以下是逐项拒绝理由（都是读代码后得出的结论，不是照抄文档）。

| 你点名/看起来可分离的对象 | 结论 | 拒绝理由 |
| --- | --- | --- |
| **四层记忆本体**：`WorkingMemory`/`EpisodicMemory`/`SemanticMemory`/`PerceptualMemory` + `MemoryManager.add/search/list/clear` | **拒绝** | 它们不是"能力"而是**数据存储契约**。`manager.add` 必须在同一进程内同时写 `memories` 行与向量库（`memory/base.py:418` 起），跨工具边界调用会把它变成两次独立 RPC：真值源成功、向量失败时无法回滚，直接破坏 `memory/embedding_lock.py` 维护的一致性。而且入参/出参是 `MemoryItem`（含 `datetime`、`Mapping` 元数据），不满足工具的严格 JSON 契约 |
| **`RAGPipeline.ingest` 本体** | **拒绝**（但其可分离部分已分离） | 它是**有状态编排**：解析 → 分块 → 双写 → LLM 抽取 → 图事实物化 → 报告，全程持有 `EntityResolver` 缓存与 embedding lock（`apply_embedding_lock`），不是单次无状态调用。可分离的"双写"已经搬成 `knowledge.hybrid_index`，剩下的编排留在管道里 |
| **`EntityResolver` 的匹配逻辑**（`_exact`/`_prefix_candidate`/`_entity_similarity` 分支） | **拒绝** | 与实例内的 `self._index`/`self._entities` 缓存强耦合，且相似度判定需要**整个实体集合**作为上下文；做成工具就得每次全量重载实体表，既是性能倒退，也会因为缓存不共享而产生与管道内不一致的结果。只分离了属性更新 |
| **`materialize_extraction`**（图事实物化） | **拒绝** | 入参是 `ExtractionResult` + `source_item`（非标量、含 `datetime`），内部是"断言/取代/撤回"三类补丁的**多步事务**，中途失败必须整体不留痕。工具契约是"一次调用一个结果"，装不下事务语义 |
| **`GraphRAGPipeline.retrieve` / `build_context`** | **拒绝** | 能力已被现有工具覆盖：`memory.rag_search` 的 `action=graph_retrieve` / `graph_context` 就是它。再注册一个只是同一实现的第二个入口，违反"一份实现"的目标 |
| **FastAPI 路由处理器**（`web/app.py` 的 20 个端点） | **拒绝** | 它们**本身就是**外部入口边界，不是内部可复用能力；把路由再包成工具只会多一层无意义的转发 |
| **`web/cleanup.py` 的 `propose_orphan_cleanup`** | **拒绝** | 只有测试调用（属公开能力且被 `tests/test_cleanup.py` 覆盖），不属于"死代码"，也不适合作为 LLM 工具（它是人工审核流程的一部分） |

## 5. 行为影响与兼容性

- **对外行为不变**：481 个测试全绿，其中包含聊天溯源面板（`web/app.py` U4 面板字段
  一字未改）、入库双写与 `vector_status`、图节点属性落地、RRF 排序与降级语义。
- **API 形状变化（内部）**：`pipeline.hybrid_retrieve(...)` → `tool.hybrid_recall.hybrid_recall(...)`；
  降级原因从 `pipeline.last_retrieval_note` 改为随返回值返回。仓库内调用方（`web/app.py`、3 个测试文件）已全部改完。
- **图节点更新语义**：`update_entity` 只 `MATCH` 不 `MERGE`，因此**不会**新增孤立节点，
  `graph_snapshot()` 的节点集合与重构前一致。
- **新增 4 个工具对聊天默认不可见**：`web/support.py` 的 `CHAT_TOOL_ALLOWLIST`（5 个旧工具）
  与 `CHAT_CONFIRMED_TOOLS`（仅 `memory.add`）**未改动**。这是刻意的：
  `knowledge.hybrid_index` / `knowledge.graph_node_update` 是写工具，而聊天回合只为
  `memory.add` 预置确认钥匙，暴露出去只会稳定地拿到 `CONFIRMATION_REQUIRED`；
  只放开两个只读工具则是任意的部分改动。四个工具通过自动发现已注册、可被 `Agent` 调用、
  可被 `tool.catalog` 列出。若要让聊天 LLM 直接用上只读的两个，
  把 `knowledge.hybrid_recall`、`knowledge.multi_recall` 加进 `CHAT_TOOL_ALLOWLIST` 即可（一行改动）。
- **回滚**：全部改动都在一次提交里，`git revert <commit>` 可整体回退；工具是新增文件，无数据迁移，
  `update_log.sqlite3` 只追加一行。
