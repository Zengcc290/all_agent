## 3. 前端工具层与关键约定

### 3.1 `withConfirmRebuild` 与嵌入锁 409 协议

- `withConfirmRebuild(path, confirm)`（1446）：`confirm` 为真时把 `confirm_rebuild=true` 拼到 query 上。
- `withEmbeddingGuard(send)`（1469）：先用 `confirm=false` 调一次；若抛出的错误满足 `err.status === 409 && err.detail.code === "embedding_lock_mismatch"`（判断在 `confirmEmbeddingRebuild` 1455–1459），弹 `window.confirm`，用户同意后用 `confirm=true` 重发。
- 使用该守卫的前端入口共 **5** 个：`/api/knowledge`(2446)、`/api/knowledge/image`(2567)、`/api/ingest`(2605)、`/api/knowledge/jobs/{id}/retry`(2489)、`/api/documents/{id}/revectorize`(2838)。
- 后端对应：`guard_embedding`(app.py:227) → `apply_embedding_lock`(embedding_lock.py:136) → 不一致且未确认时抛 `EmbeddingLockMismatch`(embedding_lock.py:25)，`to_detail()`(42) 产出 `code/locked/current` 三段，由 `raise HTTPException(409, detail=...)`(app.py:235) 抛出。确认后走 `rebuild_vector_projection`(embedding_lock.py:298) 重建集合 + 全量重灌。

### 3.2 星云图增量协议

- `loadGraph`(1569) 的 query 选择逻辑：`at` 非空 → `/api/graph?at=`；否则 `track`（`options.since` 为真且无 `at`）→ `/api/graph?since=<graph.revision>`；否则 `/api/graph`。
- 后端 `graph`(app.py:273) 用进程内 `graph_cache`(app.py:250) 按 `revision + at` 缓存 `build_graph` 结果（命中判断 275–282）；`since >= 0 && since == revision && !at` 时只回 `{revision, unchanged:true, nodes:[], edges:[]}`（约 286–293）。
- 写操作统一走 `invalidate_graph()`(app.py:255) → `bump_graph_revision()`(support.py:105)，后台抽取线程也走同一计数器（`extract_graph_patches` 内 `bump_graph_revision()` support.py:357）。

### 6.3 其它观察（不改代码，仅记录）

1. **文档注释与实现不符**：`web/app.py:5` 写「GET /api/graph-rag」，实际是 `@app.post`（app.py:304）。前端用 POST，行为一致，仅注释过时。
2. **`/api/import` 未走嵌入守卫**：前端 idx:2904 直接 `apiPostForm("/api/import", form)`，未包 `withEmbeddingGuard`；后端 `import_file`（app.py:665）内部也没有 `guard_embedding` 调用（已用 grep 核对：`guard_embedding` 在 app.py 只出现在定义处 227 与调用点 406/464/558/598/741/743，`import_file` 的 639–653 区间内没有；重嵌入端点的锁闸门已随逻辑迁至 `tool/document_revectorize.py:54`）。导入事实走 `semantic.add_fact` → `BaseMemory.add` → 向量 upsert，因此在嵌入锁不一致时可能以 Qdrant 维度错误的形式失败，而不是走统一的 409 确认流程。（是否会在实际部署中触发，取决于 Qdrant 维度状态，未实测。）
3. **`/api/import` 的 errors 未展示**：后端收集 `errors`（`note_error` tool/import_knowledge.py:83，上限 `WEB_IMPORT_ERRORS_MAX` 见 tool/import_knowledge.py:86），前端只 toast imported/skipped（idx:2905）。
4. **搜索框纯本地**：`doSearch`（idx:2372）只过滤已下发的 `graph.nodes`，不调 `/api/*`，因此搜不到 `chunks` 真值源中未被 `build_graph` 纳入节点预览的文本，也没有 FTS5/向量语义检索能力。真正的语义检索入口只有聊天面板（graphrag / offline 模式）。
5. **`/api/graph` 的 `at` 只影响图关系**：`graph-as-of-apply` 传的 `at` 只作用于 `_graph_snapshot`（Neo4j 时序快照），SQLite 侧的 `manager.list()` 仍是全量当前数据（tool/graph_snapshot.py:119–121 无时间过滤）。
6. **`checkHealth` 里 `offerEmbeddingRebuild` 只在 boot 调一次**：靠 `window.__embeddingRebuildAsked`（idx:3006–3007）去重；`checkHealth` 本身没有周期定时器，后续只在 `offerEmbeddingRebuild` 成功重建后再调一次（idx:3023）。
7. **`#doc-revectorize` 是唯一动态注入的 `<button id>`**：写在 `renderDocDetail` 的模板字符串里（idx:2812），每次打开文档详情都会重新绑定（idx:2819），因此不存在重复监听问题（旧的 `#doc-detail` innerHTML 被整体替换）。
8. **`POST /api/graph-rag` 名为「检索」但默认写图**：`_expand` 收尾会调 `_reinforce`（graph_rag.py:274–277 → 298），对最终 adopted 路径的边做 `add_relation(*key, bump=True)`（graph_rag.py:309 → graph.py:190/203 → 433），写入 Neo4j 边的 `weight`/`accessed_at`。开关 `constants.MEMORY_EDGE_REINFORCE`（constants.py:212）为 True。因此它并非纯只读端点；`POST /api/chat` 回答后的 `graph_retrieve`（app.py:349）同样带这个副作用。
9. **本轮新增工具未接入聊天白名单**：`tool/hybrid_recall.py`（工具名 `knowledge.hybrid_recall`，hybrid_recall.py:215）、`tool/hybrid_index.py`、`tool/multi_recall.py`（`hybrid_recall_multi` multi_recall.py:150）、`tool/graph_node_update.py` 都是 22:40–22:45 新增的，但 `web/support.py` 虽在 00:02:54、00:42:27 改动过，`CHAT_TOOL_ALLOWLIST`（support.py:231–239）已加入 `memory.manage`；其余知识工具仍不在聊天白名单。**因此 LLM 在聊天里看不到这些新工具**，它们目前只被 `web/app.py`（hybrid_recall，app.py:74/360）和 `memory/rag/pipeline.py`（index_chunk，pipeline.py:179/181）直接调用。这是重构进行中的中间状态，未必是最终意图。

1. **`knowledge-submit` → `POST /api/knowledge`（异步入库队列）**：前端 `submitKnowledgeSentence` → `withEmbeddingGuard` → `add_knowledge` → `guard_embedding`/`apply_embedding_lock` → `IngestJobQueue.submit`（写 `ingest_jobs`）→ 后台单线程 `_run_job` → `RAGPipeline.ingest`（经 `tool/hybrid_index.index_chunk` 写 `documents`/`chunks`/`chunks_fts`/`memories`/Qdrant）→ LLM 抽取 → `materialize_extraction` → `SemanticMemory.add_fact` → `_write_edge` → Neo4j `add_relation`+`add_observation` → `set_ingest_job_status` → `_notify` → `invalidate_graph`，最后由前端 3s 轮询 `/api/knowledge/jobs` 发现 `done` 后再触发 `loadGraph({since:true})` 整图刷新——跨 10 个模块（含新增的 `tool/hybrid_index.py`）、两条独立时间线（HTTP 请求 + 后台 worker + 轮询）。

2. **`chat-send-btn`（offline/online）→ `POST /api/chat`（知识管家 ReAct）**：`sendChat` → `chat` → `chat_ready` → `get_agent`（注册 5 个工具）→ `chat_tool_names` → `ReActAgent.run` 多轮工具调用（`memory.query`→向量库、`memory.rag_search`→`GraphRAGPipeline.retrieve`→Neo4j `path_query`、`memory.add`→写 memories+向量、`web.search`→外部联网）→ `record_qa` 写 episodic → `schedule_qa_extraction` 后台再跑一遍完整 ingest 抽取 → `invalidate_graph` → `graph_retrieve` + `hybrid_recall`（`tool/hybrid_recall.py` 内向量路 × FTS5 路 × `rrf_fuse` 融合，再按真值源回查正文）→ 前端 `appendBubble`+`appendRetrieval` 渲染依据面板。

3. **`btn-ingest`/`file-input` → `POST /api/ingest`（文档导入）**：`_save_upload` 流式落盘（含 413/400 边界）→ `guard_embedding` → `ingest_source` → `DocumentProcessor.parse`（多格式解析）→ `RAGPipeline.ingest` 逐块经 `index_chunk` 写真值源 `documents`/`chunks` + FTS5 触发器 + `memories` + Qdrant → 逐块 `build_graph_context` + LLM 抽取 + `materialize_extraction`（实体消解 / supersede / retract）→ Neo4j 边与观察 → 文档状态机 `parsed→extracted/failed` → `episodic.record` 留痕 → `invalidate_graph` → 前端 `loadGraph()` 全量重建星系树。

（并列候选：`btn-repair` → `POST /api/reconcile` → `repair_drift`，链长接近但分支少，故未列入前三。）
