## 0. 先用三句话说清项目

1. 这是一个 **FastAPI + 单页 Web 前端** 的个人知识库：可以录入文字、文档、图片和三元组，并在“知识星云”里展示实体与关系。
2. 数据分成 **SQLite 真值、向量投影、图投影**：SQLite 保存记忆、原文和分块；Qdrant/内存向量用于语义检索；Neo4j/内存图用于关系与路径检索。
3. 聊天由 **ReActAgent + 注册工具** 驱动：模型不能直接操作数据库，只能调用经过严格 Pydantic 校验、版本校验、副作用确认和请求白名单过滤的工具。

答辩时先背住这一段，再展开细节。

```text

        │

        │
        ├── RAGPipeline
        │     ├── DocumentProcessor：解析与切块
        │     ├── hybrid_index：真值 + 向量索引
        │     ├── KnowledgeExtractor：实体/关系抽取
        │     └── GraphRAGPipeline：证据 + 图路径
        │
        ├── ReActAgent
        │     ├── 请求级 tool_names 白名单
        │     ├── 文本 ReAct / OpenAI native tool calls
        │     └── ToolExecutionManager
        │           ├── schema/version/generation 校验
        │           ├── 副作用确认
        │           ├── 超时/并发/依赖调度
        │           └── 输出模型校验
        │
        ▼
MemoryManager（四层记忆，共用后端）
        ├── SQLiteDocumentStore：memories 真值
        ├── DocumentRepository：documents/chunks/FTS5/jobs/embedding_lock
        ├── QdrantVectorStore 或 InMemoryVectorStore：向量投影
        └── Neo4jGraphStore 或内存图：图投影
```

### 最重要的设计原则

**SQLite 是可持久化真值，向量和图是可重建投影。**

- `memories`：四层记忆条目及 embedding。
- `documents`：原始文档。
- `chunks`：文档分块与向量状态。
- `chunks_fts`：FTS5 关键词索引。
- `embedding_lock`：当前库属于哪个 embedding 模型/维度。
- `ingest_jobs`：一句话入库任务状态。

## 4. 推荐读代码顺序

不要从 3000 多行前端开始。按下面顺序读：

## 5. 四层记忆与三种存储

### 5.1 四层记忆

| 层 | 类 | 用途 | 典型内容 |
| --- | --- | --- | --- |
| working | `WorkingMemory` | 短期工作上下文，有默认 TTL 和容量 | 当前任务中间状态 |
| episodic | `EpisodicMemory` | 带时间的经历 | 问答记录、上传文档事件 |
| semantic | `SemanticMemory` | 可检索知识与事实 | 文档 chunk、实体、关系、三元组 |
| perceptual | `PerceptualMemory` | 感知内容 | 图片及图文 embedding |

`MemoryManager` 让四层记忆共用同一个 document/vector/graph 后端，避免不同组件各开一套库。

### 5.2 三种存储角色

| 存储 | 当前实现 | 角色 | 能否回退 |
| --- | --- | --- | --- |
| 文档/记忆真值 | SQLite | 保存原文、chunk、memory、任务和 embedding lock | 文件模式持久化；测试可用 `:memory:` |
| 向量投影 | Qdrant 或内存向量 | 相似度检索 | 未配置 Qdrant 自动用内存实现 |
| 图投影 | Neo4j 或内存图 | 实体、观察、多元角色、RELATED 边与路径 | 未配置 Neo4j 自动用内存实现 |

### 5.3 为什么不是“只用一个数据库”

- SQLite 擅长事务和持久化真值；
- Qdrant 擅长高维向量近邻搜索；
- Neo4j 擅长多跳关系与路径；
- FTS5 负责精确词、编号、专有名词；
- 混合检索把不同检索器的长处融合起来。

代价是跨存储一致性更难，所以代码里有 embedding lock、reconcile/repair 工具和大量故障测试。

## 6. 三条必须会讲的调用链

### 6.1 一句话入库

```text
POST /api/knowledge
→ embedding lock 检查
→ IngestJobQueue.submit（文件 SQLite 时）
→ RAGPipeline.ingest
→ DocumentProcessor 切块
→ tool.hybrid_index.index_chunk
   1. 写 documents/chunks 真值
   2. 写 semantic memory
   3. 写向量投影
   4. chunk 标为 indexed
→ KnowledgeExtractor.extract
→ materialize_extraction
   ├── 实体 semantic memory
   ├── 关系 semantic memory
   └── Neo4j/内存图投影
→ 写 episodic“添加了一条知识”
→ 图 revision 递增，前端轮询刷新
```

关键点：抽取失败不会丢掉已经写入的原文；报告会把错误放进 `last_ingest_report.errors`。

### 6.2 混合检索 + GraphRAG

```text
用户问题
├── 向量路：MemoryManager.search → vector_store.search
├── 关键词路：DocumentRepository.search_keywords → SQLite FTS5/BM25
├── hybrid_recall：RRF 按排名融合
└── GraphRAG：从证据/实体出发扩展关系路径
    → evidence + paths + context
```

**RRF（Reciprocal Rank Fusion）**重点不是把不同分数硬相加，而是按两路排名融合，因此能容纳“向量相似度”和“BM25 分数”这两种量纲不同的信号。

向量服务不可用时，`hybrid_recall` 会保留关键词路并在 `note` 里说明降级原因，不应伪装成完整向量检索。

### 6.3 聊天 + 工具调用

```text
POST /api/chat
→ chat_ready 检查 provider
→ get_agent（进程级 ReActAgent）
→ chat_tool_names 生成本请求精确白名单
→ agent.run / run_with_react
→ 模型输出 Thought/Action/Action Input 或 native tool_call
→ ToolExecutionManager 严格校验并执行
→ Observation 回给模型
→ Final Answer
→ 完整回合写 episodic QA
→ 后台抽取问答中的图知识
```

Web 聊天只暴露：

- `memory.query`
- `memory.add`
- `memory.manage`
- `memory.rag_search`
- `memory.rag`
- `web.search`（只有联网模式且搜索已配置）

项目其余工具不会因为已注册就自动暴露给聊天模型。`tool_names=[]` 表示本请求没有任何工具，`system.tool_catalog` 也不会被隐式放开。

## 7. 工具系统：这个项目最值得讲的部分

### 7.1 一个工具的标准结构

每个可发现工具放在一个 `tool/*.py` 直接子模块中，并包含：

```python
TOOL_ENABLED = True

class Input(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)

class Output(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)

class SomeTool(BaseTool):
    spec = ToolSpec(
        name="namespace.action",
        description="...",
        version="1.0.0",
        input_model=Input,
        output_model=Output,
        side_effect="read",  # 或 write / destructive
    )

    def execute(self, arguments: Input) -> Output:
        ...

def create_tool() -> BaseTool:
    return SomeTool()
```

发现器只扫描 `tool` 包的直接子模块：

- `_` 开头、`base` 和子包会忽略；
- `TOOL_ENABLED` 必须是布尔值；
- `create_tool()` 必须零参数可调用；
- 一个插件失败不会隐藏其他健康插件；`strict=True` 时最终统一报错。

### 7.2 当前 28 个工具

`web.search`

### 7.3 哪些函数值得工具化

适合工具化的函数通常满足：

1. 有明确业务能力名称；
2. 输入/输出能稳定 JSON 化；
3. 需要让 LLM 主动选择调用；
4. 可定义副作用、超时、幂等和并发语义；
5. HTTP、脚本和 Agent 可以复用同一实现。

当前典型例子：`hybrid_recall`、`build_graph`、`reconcile_report`、`repair_drift`、文档查询/重嵌入、导入/导出。

不适合工具化的通常是：纯格式化、内部小 helper、连接管理、缓存失效、锁操作、路由专属的 HTTP 错误映射。

### 7.4 Runtime 到底检查什么

`ToolExecutionManager.execute_batch` 执行顺序可以记成：

1. `call_id` 去重；
2. 工具是否注册；
3. version / schema hash / registry generation 是否过期；
4. Pydantic `strict=True` 校验参数；
5. 副作用确认；
6. 依赖图和环检测；
7. 并发/串行调度；
8. timeout 与重试语义；
9. 输出模型校验；
10. 返回统一 `ToolResult`。

### 7.5 普通写确认和破坏性确认

- `side_effect="read"`：免确认。
- 普通写工具：确认键绑定工具版本、schema hash 和注册 generation。
- `side_effect="destructive"`：还必须绑定**规范化后的精确参数摘要**。

因此确认“删除 A”不能被模型替换成“删除 B”，也不能从 `delete` 升级成 `clear`。

Web 的删除流程是两步：

1. 第一次调用返回 `CONFIRMATION_REQUIRED` 和精确参数，且不写 QA、不触发后台抽取；
2. 浏览器 `window.confirm` 获得用户同意后，把同一 `tool_name + arguments` 回传，再执行一次。

## 8. Embedding lock 为什么重要

向量库里的所有向量必须处于同一个 embedding 空间。换模型或维度后，旧向量和新向量不能静默混用。

当前守卫会比较：

- SQLite `embedding_lock` 记录的模型与维度；
- 当前 embedding 实现；
- Qdrant 实际 collection 维度；
- 已存在 memory/chunk/vector 数据。

关键规则：

- 空库可写入当前 lock；
- 非空但无 lock 的旧库被视为未知空间，必须确认重建；
- 不匹配时写接口返回 409；
- 用户确认后重建唯一 ID 集合 `chunks ∪ memories`；
- 孤立 chunk 会补成可持久化、重启后仍能召回的 semantic memory；
- 重建期间写 `__rebuild_in_progress__` 哨兵；
- 只有向量投影全部成功后，SQLite memory embedding 才用一个事务批量提交并写最终 lock。

常用操作：

```powershell
python scripts/reindex_embeddings.py --help
python scripts/migrate_to_cloud.py --help
```

遇到前端 409 时，不要删除数据库或强行改维度；先确认是否确实更换了模型，再通过页面确认或调用：

```text
POST /api/embedding/rebuild?confirm_rebuild=true
```

## 10. 前端怎么理解

前端不是 React/Vue 工程，而是一个静态单页：`web/static/index.html`。

它主要做五件事：

1. Canvas 绘制星云实体与关系；
2. 调 `/api/graph`，通过 `revision/since` 避免每 20 秒重复传全图；

4. 展示 GraphRAG 来源、路径和混合检索分数；

后端必须先注册所有 `/api/*`，再把 `/` 挂到 `StaticFiles`，否则静态路由会吞掉 API。

## 13. 高频答辩问题与短答案

### Q1：为什么要四层记忆？

为了区分生命周期和用途：working 是短期上下文，episodic 是带时间的经历，semantic 是稳定知识，perceptual 是图片等感知数据。它们共用后端，但查询、TTL 和语义不同。

### Q2：为什么 SQLite 里也存 embedding？

SQLite 行是可恢复真值的一部分；向量投影丢失或模型重建时，可以从持久行和 chunks 重建。真正相似度查询仍走向量 store。

### Q3：为什么还要 FTS5？

向量擅长语义改写，FTS5 擅长精确词和编号；向量服务故障时，FTS5 还是本地可用的降级路线。

### Q4：GraphRAG 比普通 RAG 多了什么？

普通 RAG 返回相似 chunk；GraphRAG 还从实体出发扩展关系边和路径，让答案能说明“哪些实体如何关联”。

### Q5：为什么 `ToolSpec` 要保存 schema hash 和 generation？

schema hash 防止输入/输出契约变化后继续执行旧调用；generation 防止同名工具实现被替换后复用旧确认。

### Q6：为什么删除确认还要绑定参数？

只绑定工具名会让模型拿“删除 A”的授权改成“删除 B”或 `clear`。当前用规范化 JSON 的 SHA-256 把批准绑定到精确调用。

### Q7：为什么换 embedding 模型要重建？

不同模型和维度不在同一个向量空间，相似度没有意义。embedding lock 用 409 阻止静默混用。

### Q8：项目怎么离线运行？

SQLite + HashEmbedding + 内存向量 + 内存图可以离线启动；聊天和 LLM 抽取需要 provider，联网搜索需要 search 配置。

### Q9：为什么 Web Agent 不自动发现全部工具？

最小权限。Web 只注册并白名单放行聊天真正需要的 memory/RAG/search 工具，文件系统和维护工具不会暴露给用户聊天。

### Q10：如何证明代码质量？

当前 `ruff` 全绿、520 个 pytest 通过；关键边界有端到端测试，包括 Web→真实 ReAct→工具、精确删除确认、embedding 重建失败和白名单旁路。

## 14. 当前版本的真实边界（不要在答辩中过度承诺）

这些不是“项目不能用”，而是必须如实描述的工程边界：

1. **不要把 Uvicorn 开成多个 worker 共同消费一句话队列。** 当前 `IngestJobQueue` 是单进程、单线程串行设计；多进程共享同一 SQLite 时还缺少原子 claim、owner lease 和 fenced completion。
2. **SQLite/Qdrant/Neo4j 之间没有分布式事务。** 已有重建、对账和部分补偿，但远程删除在极端失败下仍可能产生临时或永久投影漂移；重要数据操作前应备份 SQLite，并用 `/api/reconcile` 检查。
3. **权限字段目前是元数据，不是访问控制。** 真正生效的是 Web 工具白名单和 side-effect confirmation，不能宣传成多租户 RBAC。
4. **图 revision/cache 是进程内状态。** 单进程本地应用成立，多进程部署需要共享 revision 或消息机制。
5. **聊天 Agent 是进程级单例并共享历史。** Web 用 `asyncio.Lock` 串行化请求，适合单人本地应用，不是多用户会话隔离方案。
6. **HashEmbedding 是离线兜底，不是高质量生产语义模型。** 演示可用；正式语义检索应配置云端 embedding 并确认重建。
7. **工具 `permissions` 尚不执行授权。** 不要把它和副作用确认混为一谈。

最稳妥的演示方式：**单进程启动、先跑 `/api/health`、使用本地 SQLite、必要时配置一个稳定的聊天模型，演示前不要临时更换 embedding 模型。**

### 16.8 下午阅读时怎样使用这份词典

遇到一条链，例如：

```text
knowledge-submit → submitKnowledgeSentence → add_knowledge
→ IngestJobQueue.submit → RAGPipeline.ingest
→ index_chunk → BaseMemory.add → SQLite/Qdrant
```

不要立刻展开每个实现。先从上表给每个名字贴职责标签：

```text
提交表单 → HTTP 路由 → 持久任务 → 入库编排
→ 单块索引 → 通用记忆写入 → 真值/向量投影
```

如果你能把函数名翻译成这条“职责句”，就算第一遍读懂；只有当你回答不了“输入是什么、输出是什么、会写哪个存储”时，才进入函数体继续读。
